# Ableton Live and Max external conformance model

This document is Sunny's adversarial external-alignment record. The formal IR specifications define
what Sunny means; this document asks whether Ableton Live, Max for Live, Max/MSP, and RNBO can
actually realise each relevant property, under which conditions, and with what evidence. It was
last reviewed on 2026-09-01 against the Live Object Model documentation identified as Live 12.3.5
and the Max SDK 8.2.0 MSP-object callback contract.

## 1. Evidence and confidence language

Sunny uses four distinct evidence levels. They must not be conflated:

1. **Documented** — an operation is present in an authoritative Ableton or Cycling '74 reference.
2. **Modelled** — Sunny derives a capability from an observed Live version and a documented version
   threshold.
3. **Contract-tested** — Sunny's native request, wire frame, Python translation, and fake Live object
   agree in automated tests.
4. **Live-validated** — the operation has been observed in a named Live build on a named platform.

The repository currently has levels 1–3. It does not claim level 4. A successful loopback test is
not evidence that an installed Live edition contains a particular native device or accepts its UI
name.

The 2026-09-01 recheck found no source-model contradiction in the current official host guidance:
Ableton now recommends/bundles Max 9 for Live 12, while Cycling '74 still documents the same four
preconditions for sample-accurate event-to-audio scheduling and warns that entering/leaving Max for
Live preview may disrupt timing continuity. Sunny therefore records exact observed Max/Live
versions rather than promoting its `max-test` minimum Max 8.2 into a supported-host certification.
The closed host-run plan measures those scheduler and preview conditions; it does not mark them
validated.

Tractability is classified separately:

| Class | Meaning |
|---|---|
| A — static | Decidable from a validated Sunny document and a fixed public-API rule |
| B — handshake | Decidable from the connected Live version reported by the documented Application object |
| C — call outcome | Decidable only when the target accepts or rejects the exact operation |
| D — observed target state | Decidable for a selected scalar only by typed readback from a named running target |
| E — host/render evidence | Requires installed artefacts, licence/edition facts, platform, host tests, and, for sonic claims, rendered audio criteria |
| F — unavailable | Not discoverable or expressible through Sunny's current external contract |

## 2. End-to-end system model

```text
Score / Timbre / Mix intent
          │ validate (A)
          ▼
Ableton compiler ── target-profile preflight (B) ── capability-preserving plan
          │
          ▼
native TCP transport ── versioned Sunny wire contract ── Python Control Surface adapter
                                                          │
                                      version-coupled private host API
                                                          │ main-thread schedule
                                                          ▼
                                            documented Live Object Model

Optional future render/control path:
formal Sunny render model ── Max external or RNBO export ── Max for Live device ── Live audio/parameters
```

The rightmost public contract is the [Live Object Model](https://docs.cycling74.com/apiref/lom/).
The current native-to-Live host adapter is not itself a public LOM client: it is a third-party
Control Surface script hosted by Live's Python runtime. Ableton documents how to
[install third-party Remote Scripts](https://help.ableton.com/hc/en-us/articles/209072009-Installing-third-party-remote-scripts),
but does not publish `_Framework.ControlSurface` as a stable third-party programming contract.
Therefore Sunny labels this adapter `version_coupled_private` and refuses to activate its
synchronous test fallback when a Live runtime is present.

The bridge's `sunny_get_target_profile` handshake calls the documented
[Application version functions](https://docs.cycling74.com/apiref/lom/application/) and returns the
observed version, bridge protocol, adapter contract, and conservative capability states. The native
peer rejects a wrong protocol, unexpected adapter identity, or feature claims inconsistent with the
observed version. Score, Timbre, and Mix compilation also reject an absent profile before the first
mutation: inability to observe a capability is not evidence that the capability is available.
Offline command recording uses an explicit modelled profile and labels it as such. Every compiler
also revalidates profiles returned by custom in-memory transports, so bypassing the JSON parser does
not bypass version/capability consistency checks.

Bridge protocol v4 added `sunny_get_target_snapshot`, a read-only observation assembled during one
synchronous main-thread call whose fields
are limited to documented [Song](https://docs.cycling74.com/apiref/lom/song/),
[Scene](https://docs.cycling74.com/apiref/lom/scene/),
[Track](https://docs.cycling74.com/apiref/lom/track/),
[ClipSlot](https://docs.cycling74.com/apiref/lom/clipslot/),
[Clip](https://docs.cycling74.com/apiref/lom/clip/),
[Device](https://docs.cycling74.com/apiref/lom/device/),
[MixerDevice](https://docs.cycling74.com/apiref/lom/mixerdevice/),
[DeviceParameter](https://docs.cycling74.com/apiref/lom/deviceparameter/),
[CuePoint](https://docs.cycling74.com/apiref/lom/cuepoint/), and
[TuningSystem](https://docs.cycling74.com/apiref/lom/tuningsystem/) reads. It is a deployment precondition,
not a lock or a claim that Live exposes compare-and-swap. The native trust boundary additionally
enforces Song's documented 20–999 BPM domain.

The current Python adapter's compatibility target is Live 11 and 12. Ableton's Remote Script
guidance identifies Python 3 for Live 11+, and Sunny uses Python 3-only syntax. The model defines
the note capability below Live 11 so alternative/test transports degrade coherently; that is not a
claim that this Remote Script can be installed in Live 10.

### 2.1 Closed bridge algebra (protocol v43)

The bridge is not a generic reflection proxy for the Live Python object graph. Every request and
response carries `bridge_protocol_version: 43`; a missing, Boolean, older, newer, or otherwise
malformed version is rejected. Request fields are exactly `bridge_protocol_version`, `type`,
`path`, `name`, and optional `args`. Response fields are exactly
`bridge_protocol_version`, `success`, and either `value` or `error`. The native peer rejects a
wrong-version, contradictory, unknown-field, missing-error, or integer-narrowing response. Both
peers enforce the same 16 MiB maximum UTF-8 JSON frame payload.

Paths are canonical, rooted at `song`, and use canonical non-negative decimal indices. Relative
paths, leading slashes, empty segments, leading-zero indices, reflective names such as
`__class__`, and descendants outside this table fail before object traversal:

| Path shape | Allowed reads | Allowed writes | Allowed calls |
|---|---|---|---|
| `song` | `tempo`, signature numerator/denominator, `is_playing`, `current_song_time` | `tempo`, signature numerator/denominator | profile/snapshot handshakes, `sunny_get_scene_count`, `sunny_get_return_track_count`, `sunny_set_cue`, `create_scene`, `create_midi_track`, `create_return_track` |
| `song/scenes/N` | — | `name`, `tempo_enabled`, `time_signature_enabled` | — |
| `song/tracks/N` | — | `name`, `mute`, `solo`; exact Boolean `arm = false`, `implicit_arm = false` | `insert_device`, `sunny_get_device_count`, `sunny_set_output_routing_type`, `sunny_set_output_routing_channel` |
| `song/return_tracks/N` | — | `name`, exact Boolean `mute = false`, `solo = false` | `insert_device`, `sunny_get_device_count`, `sunny_set_output_routing_type`, `sunny_set_output_routing_channel` |
| `song/master_track` | — | — | `insert_device`, `sunny_get_device_count` |
| `song/tracks/N/clip_slots/M` | — | — | `create_clip`, `delete_clip` |
| `song/tracks/N/clip_slots/M/clip` | — | `name`, signature numerator/denominator, `start_marker`, `end_marker`, `looping`, `muted`; on Live 11+, exactly Trigger `launch_mode`, None `launch_quantization`, false `legato`, floating-zero `velocity_amount`, and null `groove` | `add_new_notes`, closed `get_notes_by_id` and `get_all_notes_extended` readback, no-argument `sunny_clear_all_envelopes`; snapshot-only public media/location identity and derived `end_time` are read directly by `sunny_get_target_snapshot` |
| normal/Return `mixer_device` | — | exact integer `crossfade_assign = 1`; exact integer `panning_mode = 0` | — |
| Master `mixer_device` | — | exact integer `panning_mode = 0` | — |
| track-like `mixer_device/volume` | — | `display_value` | — |
| normal `mixer_device/track_activator` | — | exact floating `value` in {0.0, 1.0} | — |
| Return/Master `mixer_device/track_activator` | — | exact floating `value = 1.0` | — |
| normal/Return `mixer_device/panning` | — | finite numeric `value` | — |
| Master `mixer_device/panning` | — | exact floating `value = 0.0` | — |
| track `mixer_device/sends/N` | — | `display_value` | — |
| track-like `devices/N` | — | — | read-only `sunny_get_device_parameter`, mutating `sunny_set_device_parameter` |

`devices/N` is a Sunny adapter path over the insertable chain, not an unchecked raw list offset.
Cycling '74 documents `Track.devices` as including the separately exposed mixer device, so protocol
v20 filters that exact mixer child consistently in snapshots, counts, and path traversal.

Protocol v42 retains v5's closed operation algebra and validates the complete argument shape before Live lookup or mutation: documented
20–999 BPM, signature numerators 1–99 and denominators in {1, 2, 4, 8, 16}, finite positive clip/note durations, finite non-negative quarter-note positions,
MIDI pitch 0–127, Sunny velocity 1–127, Boolean mute/solo, exact false ordinary/implicit arm state, exact eight-field deterministic note dictionaries,
non-empty device/parameter names, coherent parameter ranges, and the exact generated-Clip launch
tuple `(Trigger, None, legato off, velocity amount 0.0)`. Whole-MixerDevice writes are limited to
exact integer crossfade-neutral assignment `1` on normal/Return Tracks and Stereo Pan mode `0` on
normal/Return/Master. Boolean, floating, A/B crossfade, and Split Stereo pan forms are rejected.

Output routing is a two-call transaction because changing the type may change the advertised
channel collection. `sunny_set_output_routing_type` accepts one exact
`{display_name, identifier}` dictionary, requires it in the Track's current advertised type
collection before mutation, and returns the requested type, the pre-mutation type collection, and
a closed post-set routing snapshot. `sunny_set_output_routing_channel` accepts the same expected
type plus one exact channel dictionary, revalidates the selected type and both current
collections, then returns the requested pair, pre-channel selection/collections, and the closed
final snapshot. The native peer independently closes and checks every nested shape, echo,
membership relation, type-stability condition, and exact readback. A successful type call followed
by a failed channel call remains journalled as a possible partial target mutation.
Generated Part Tracks additionally lower their Boolean mute intent to exact floating Track
Activator values (`mute ? 0.0 : 1.0`). Generated Aux returns and the Main Track require exact
floating `1.0`; Main panning requires exact floating `0.0`, while normal/Return pans remain finite
modeled scalars. Generated Aux returns additionally use only exact false mute/solo writes.
`muted_via_solo` remains observation-only; Return arm and arbitrary Track properties remain outside
the algebra.
This is narrower than the public
LOM on purpose. A capability absent from the table must first enter the Sunny model, receive
preconditions and result semantics, and advance the protocol; constructing a generic native
`LomRequest` does not broaden the peer contract.
The envelope adapter accepts no arguments, calls the public `Clip.clear_all_envelopes()` method,
then returns an exact one-member object containing Boolean `has_envelopes`; method acceptance alone
is not absence evidence.
The native protocol implements the same complete path/operation/argument predicate. Recording,
journalled, and TCP transports apply it before accepting a command, so malformed or out-of-algebra
native requests are `not_sent`; the Python predicate remains an independent second trust boundary.

The legacy Orchestrator queue has an additional checked pre-wire boundary. Its dispatcher requires
canonical paths and complete message shapes, parses clip length as one finite positive token, and
converts NoteEvent timing without calling assertion-bearing rational helpers. Empty or invalid note
batches are reported as not sent. The Python peer remains independently authoritative and repeats
the closed-algebra validation before any Live object lookup.

## 4. Max/MSP, Max for Live, and RNBO boundary

Max is not one interchangeable target. Four contracts must be kept separate:

| Target | What it can legitimately do | Preconditions | What it does **not** prove |
|---|---|---|---|
| Max for Live patch/device | Instruments, MIDI/audio effects, MIDI Tools, public LOM access through `live.path`, `live.object`, `live.observer`, `live.remote~`, or LiveAPI JavaScript. | Max for Live available; a deployable `.amxd`; correct device kind; main-thread/deferred LOM scheduling; frozen dependencies for distribution. | It is not insertable through `Track.insert_device`, and its availability is not reported by the Application version handshake. |
| Native Max/MSP external | A C/C++ Max object with message or DSP entry points. Cycling '74's [Max SDK](https://github.com/Cycling74/max-sdk) builds `.mxo` on macOS and `.mxe64` on Windows and recommends host testing. | Supported Max SDK/toolchain, platform binaries, package layout, reference/help files, and Max host tests. A Max for Live wrapper is additionally required to participate in Live. | A compiled external alone neither edits a Live Set nor establishes a public LOM integration. It is not a Linux runtime target. |
| RNBO C++ export | Generated portable DSP code from an RNBO patcher, suitable for an application or plug-in integration. | An authoritative RNBO patch, export tooling, generated source, parameter/event contract, and render tests. See the [RNBO C++ target](https://rnbo.cycling74.com/learn/the-cpp-source-code-target-introduction). | RNBO export is not a substitute for Live session authoring, LOM navigation, or Sunny's Score/Timbre/Mix document model. |
| Standalone Max application | General Max/MSP execution outside Live. | Full Max licence and platform deployment. Max for Live-only authorisation has documented restrictions. | Behaviour in standalone Max does not establish behaviour inside Live's Max for Live host. |

The [Max for Live API overview](https://docs.cycling74.com/userguide/m4l/live_api_overview/)
states that not all Live parameters are exposed, LOM changes cannot be triggered directly from a
notification, and deferred scheduling is required in those paths. The
[Max for Live limitations](https://docs.cycling74.com/userguide/m4l/live_limitations/) also rule out
assumptions such as using `send~`/`receive~` to pass audio between devices. A distributable device
must follow Cycling '74's [freezing/dependency model](https://docs.cycling74.com/userguide/m4l/live_freezing/).

Timing claims require another independent contract. Max's current
[sample-accurate messages guidance](https://docs.cycling74.com/userguide/sample_accurate_messages/)
conditions sample alignment on scheduler/audio settings and supported event paths. The Sunny
modulation externals classify their control inlet as serialized message publication and their one
outlet as an audio signal; controls apply at the next vector boundary, not an intra-vector offset.
Their callback bans allocation, locking, I/O, Max calls, and unbounded work. Passing Sunny's C++ and
SDK-header tests still does not establish the host scheduler arrangement or timing properties.
The current [Scheduler and Priority](https://docs.cycling74.com/userguide/scheduler/) guide makes
the high-/low-priority and Scheduler-in-Audio-Interrupt configurations explicit, while the
[Max SDK 8.2 threading contract](https://sdk.cdn.cycling74.com/max-sdk-8.2.0/chapter_threading.html)
states that an audio perform routine has restricted thread protection and may communicate back to
Max only through a clock. Sunny's no-allocation/no-blocking rule is a deliberately stronger
real-time design obligation, not a claim that the host enforces it for us.

Consequently, the unsafe legacy Sunny Max/RNBO prototypes remain removed. They had no maintained
`.amxd` peer, generated-code provenance, platform package, or host-level tests. The narrow
`sunny.lfo~`, `sunny.adsr~`, message-driven `sunny.hold~`, local-position `sunny.clock~`, and
global-ITM `sunny.events` SDK objects are a new implementation admitted only after satisfying
the tractable source gates below; broader reintroduction still requires all of the following, not
merely a CMake option:

1. one named user-facing capability that the existing public-LOM bridge cannot provide;
2. a formal parameter, event, timing, and thread model backpropagated into a Sunny IR or render API;
3. a real Max package and, for Live use, a frozen Max for Live device;
4. pinned SDK/export-tool versions and macOS/Windows artefacts;
5. Max host tests plus a named Live/Max for Live validation matrix;
6. explicit degradation when Max for Live is absent or the device was not pre-installed.

The implemented native package begins with signal-rate modulation generation, not session
construction. A future Max for Live wrapper may use `live.remote~` only for semantics that
intentionally bypass undo/automation, and must not be described as writing Sunny automation lanes.

The maintained native source and adapter model is specified in
`docs/formal/sunny-render-model.md`. Its tick transport deliberately promises block-quantised
callbacks, not intra-vector sample offsets. Modulation adapter tests establish pure recurrence,
bounded ordered transfer, overflow, and source lifecycle semantics; clock-adapter tests additionally
establish the local start-of-sample position recurrence and its explicit non-host boundary.
ITM-adapter tests establish the 64-command/256-event bounds, strict-future admission, injective
PPQ-to-host conversion, atomic note pairs, ordered one-shot callback grouping, clear ordering, and
producer serialization. `sunny.events` binds that model to pre-created permanent time objects on
the unnamed global ITM transport.
SDK-header compilation checks the wrappers against the pinned public declarations. These do not
discharge Max host-thread, vector scheduling, latency, binary loading, or signal-equivalence
obligations.

### 4.2 Corpus and style-profile external alignment

Corpus IR is source-side analytical evidence, not a Live Object Model. Ableton's documented
[Clip](https://docs.cycling74.com/apiref/lom/clip/) note reads can expose selected MIDI-note facts,
and the public object model exposes selected Set, track, device, parameter, and mixer state. It
does not thereby supply Sunny's Roman-numeral analysis, enharmonic/key interpretation, formal
sections, thematic identity, voice-leading resolutions, orchestral-combination semantics, or
composer attribution. Conversely, a field-complete Sunny Corpus JSON document proves neither that
Live accepted the resulting project nor that Max reproduced its musical interpretation.

The boundary is therefore backpropagated as follows:

| Claim | Required evidence | Current status |
|---|---|---|
| A `StyleProfile` is internally current | Exact deterministic rebuild from unique analysed membership plus C14/C15 validation | Implemented and contract-tested |
| Corpus MIDI timing loss is fully reported | Exact rational grid selection plus separate measured onset and duration RMS residuals; zero migrated legacy duration evidence must be identified as a schema default | Implemented in schema v4 and contract-tested; it does not establish Live/Max timing equivalence |
| A style field was automatically inferred | The Score analyser populated its named `WorkAnalysis` carrier; a persisted/default value is insufficient | Field-specific; the Corpus specification classifies automatic, supplied-carrier, and unavailable dimensions |
| A profile informed a Live deployment | The agent produced a valid ProjectView whose resulting Score/Timbre/Mix intent can be traced to the query; the profile itself is not sent to Live | Trace/provenance is not currently represented as a Live contract |
| Live structurally realised that project | The existing guarded compiler, operation evidence, final readback, and named Live validation conditions | Contract-tested; named-host validation still required |
| A Max/MSP or Max for Live analyser validates Corpus semantics | A versioned adapter must define its input event/audio coordinate system, analysis output schema, scheduling/thread rules, confidence, and exact mapping into WorkAnalysis, then pass named-host tests | Unimplemented; no inference is claimed |
| Rendered audio proves composer-style equivalence | A declared perceptual/statistical criterion, render path, references, uncertainty, and evaluation protocol | Outside the current model |

No current bridge request imports a Live Set into Corpus IR, writes a StyleProfile into Live, or
uses Max-derived observations to refresh one. Live note readback remains target-state evidence for
deployment verification, not retrospective musicological ground truth. A future round-trip must
define loss and identity across `Live Clip → Score IR → WorkAnalysis` and must not merge production
state with compositional style fields merely because both are observable in the same host.

plus contract-tested translation—not a live Ableton end-to-end certification.

## 7. Max named-host validation record required for runtime claims

Max evidence uses the independent C++ `MaxValidationRecord` schema 1. One record represents one
exact standalone Max or Max for Live run and retains:

- current Sunny/package versions, a nonzero 40- or 64-hex source revision, the SHA-256 of the exact
  distributable package archive,
  UTC timestamp, and named harness;
- Max and conditional Live/Max for Live versions, supported operating-system/architecture pair,
  audio driver, sample rate, I/O and signal vector sizes, Overdrive, and Scheduler in Audio
  Interrupt;
- the ordered five maintained object names, package-relative binary paths, SHA-256 values, and
  separate discovery/instantiation observations;
- the ordered 19-check host contract spanning class/selector discovery, signal topology and DSP
  lifecycle, disconnect/reconnect, controls, active teardown, ITM scheduling/order/reuse,
  release-velocity formatting, timing, downstream MIDI, rendered audio, and the conditional
  standalone/Live transport obligations;
- a non-empty summary for every check and a relative path plus SHA-256 for every passed or failed
  observation. Not-run and host-inapplicable checks carry no fictional evidence.

The `complete` member is derived: no reserved example provenance may remain, all binaries must be
discovered and instantiated, every
applicable check must pass, and exactly the opposite-host identity check must be
`not_applicable`. The strict parser rejects extensions, missing/reordered closed sets, integral
sample-rate substitution, Boolean-as-integer confusion, unsupported Windows ARM64 claims,
absolute/traversing paths, zero/uppercase hashes, asymmetric evidence pairs, and a forged derived
verdict. The same authority is available to installed Python tooling as
`sunny_native.validate_max_validation_record_json`.

Host facts first enter the independent `MaxValidationObservation` schema 1. That schema has the
same closed provenance, environment, artifact, and check order, but deliberately omits the package
archive digest, every binary/evidence digest, and `complete`. `sunny-max-evidence assemble` consumes
that observation plus the exact archive, extracted package root, and evidence root. It hashes only
regular file leaves confined to those roots and emits the final canonical record on stdout.
`sunny-max-evidence verify` re-reads the same byte set and rejects any digest mismatch. This removes
manual hash transcription as an authority; it does not observe Max, judge a check, authenticate the
harness, or guarantee an atomic snapshot across several changing files.
